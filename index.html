Inside the pantry / storage & limits

Files are split into fixed 16 KiB chunks addressed by SHA-256. Identical chunks share one stored blob across files, snapshots, and collections. A SQLite transaction publishes the complete manifest and chunk catalog. An expected-version check rejects stale saves.

Chunks are written through temporary files and atomic replacement before the manifest commits. A failed transaction can leave unreferenced chunk files; storage accounting reports them. There is no deletion or garbage collection. Back up the entire data directory while the service is stopped.

Verification checks manifest integrity, each chunk's size and hash, and each reconstructed file's hash. ZIP restoration completes these checks before offering a download. Hashes detect accidental corruption; they do not authenticate against someone who can rewrite the database and blobs.

Use portable relative paths with up to four components: ASCII letters/digits/underscores initially, then letters, digits, dots, spaces, underscores, or hyphens. Hidden names, traversal, device names, trailing dots/spaces, case-insensitive collisions, and file/directory conflicts are rejected. ZIPs preserve file bytes and logical paths, not original timestamps, permissions, symlinks, or directory metadata.

This local store allows 200 snapshots. It is not encrypted, replicated, or authenticated, and is not a substitute for an independent backup. Requests stay on loopback. The comparison checks manifests rather than rereading file content; Verify and Restore perform content checks.
